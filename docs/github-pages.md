# Публикация на GitHub Pages (статический хостинг)

Дополнение к руководству по развёртыванию (0.01.04, 2026-11-11). «Конструктор
СКИБ» — приложение без серверной части: `next build` с `output: "export"`
создаёт статический каталог `out/`, который размещается на любом статическом
хостинге (вариант В1 руководства по развёртыванию). GitHub Pages — бесплатный
вариант такой публикации, работающий из России; после разовой настройки сайт
обновляется автоматически при каждом `git push`.

Адрес сайта: `https://<логин>.github.io/<имя-репозитория>/` (сайт проекта)
или `https://<логин>.github.io/` (личный сайт, раздел 4).

## 1. Что понадобится

- Аккаунт GitHub. Для бесплатной публикации репозиторий должен быть
  **публичным** (для приватных нужен платный план).
- Git (`git --version`).
- Node.js 22.12+ — только для ручного варианта (раздел 3) и локальной
  проверки (раздел 5).
- Каталог `out/` в репозиторий **не** кладётся — он собирается заново при
  каждой публикации.

## 2. Вариант А — GitHub Actions (рекомендуется)

В поставке уже есть готовый workflow `.github/workflows/gh-pages.yml`: он сам
устанавливает зависимости, собирает `out/` с базовым путём
`/<имя-репозитория>`, добавляет `.nojekyll` и публикует сайт.

1. Создайте публичный репозиторий, например `skib-lab` (GitHub →
   New repository).
2. Загрузите исходники из распакованного архива:

   ```bash
   cd skib-lab
   git init -b main
   git add .
   git commit -m "Конструктор СКИБ 0.01.04"
   git remote add origin https://github.com/<логин>/skib-lab.git
   git push -u origin main
   ```

3. Включите Pages: **Settings → Pages → Build and deployment → Source:
   GitHub Actions** (один раз).
4. Workflow запустится сам при первом push (или вручную: вкладка **Actions →
   Deploy to GitHub Pages → Run workflow**). Сборка занимает 2–5 минут.
5. Откройте `https://<логин>.github.io/skib-lab/` — ссылка также показывается
   в журнале шага deploy.

Обновление версии: внесите изменения и выполните `git push` — сайт
пересоберётся и обновится автоматически. Имя репозитория workflow подставляет
в `BASE_PATH` сам; если репозиторий переименовать, адрес сайта тоже сменится
(localStorage-проекты пользователей при этом не переносятся — см. раздел 6).

`README.md` в корне репозитория — это нормально: он остаётся на вкладке Code
и на сайт не попадает (в публикуемый каталог `out/` не входит). Но если
Source оставить в режиме «Deploy from a branch» с веткой `main`, вместо
инструмента будет открываться README — в исходниках нет `index.html`, и
GitHub рендерит `README.md` как главную страницу (см. раздел 7). Папка
`.github` — скрытая: при загрузке файлов через веб-интерфейс проверьте, что
она действительно попала в репозиторий.

## 3. Вариант Б — ручная публикация ветки gh-pages

Если CI не нужен: собрать локально и опубликовать готовый `out/` утилитой
`gh-pages` (она публикует каталог в ветку `gh-pages` вашего репозитория).

1. Соберите статический экспорт с базовым путём (имя после `/` должно
   совпадать с именем репозитория):

   ```bash
   BASE_PATH=/skib-lab make build
   ```

2. Опубликуйте каталог — ключ `--nojekyll` добавит файл `.nojekyll`, чтобы
   GitHub не удалял служебные каталоги `_next/*`:

   ```bash
   npx --yes gh-pages -d out --nojekyll
   ```

   При первом запуске утилита запросит вход GitHub (браузерная авторизация
   или токен; можно работать и по SSH-remote).

3. Включите Pages: **Settings → Pages → Build and deployment → Source:
   Deploy from a branch → Branch: gh-pages, / (root)** → Save.

Каждое обновление — повтор шагов 1–2.

## 4. Вариант В — личный сайт `<логин>.github.io`

Если репозиторий назвать `<логин>.github.io`, сайт откроется в корне без
подпапки, и `BASE_PATH` не нужен:

- в workflow (вариант А) удалите блок `env` у шага сборки;
- в ручном варианте (Б) собирайте просто `make build` и публикуйте
  `npx --yes gh-pages -d out --nojekyll`.

## 5. Локальная проверка перед публикацией

```bash
BASE_PATH=/skib-lab make build
make preview   # http://localhost:4173
```

Убедитесь, что сайт открывается по подпапке `/skib-lab/` и ассеты грузятся:
в HTML пути должны иметь вид `/skib-lab/_next/...`.

## 6. Ограничения и особенности GitHub Pages

| Параметр | Значение |
| --- | --- |
| Размер сайта | до 1 ГБ (поставка — несколько МБ) |
| Трафик | 100 ГБ/мес, мягкий лимит |
| Сборки | не более 10 в час |
| Репозиторий | публичный на бесплатном плане |
| Тип содержимого | только статика — совпадает с архитектурой инструмента |

Важно про данные пользователя: состояние живёт в localStorage браузера и
привязано к адресу сайта. При смене адреса публикации (переименование
репозитория, переезд на другой хостинг) автосохранённые проекты не
переносятся — сданный `state.yaml` открывается через «Открыть состояние…».

## 7. Устранение неполадок

| Симптом | Причина | Решение |
| --- | --- | --- |
| Белая страница, в консоли 404 на `_next/static/...` | сборка без `BASE_PATH` или путь не совпадает с подпапкой | пересобрать с `BASE_PATH=/<имя-репозитория>` (workflow делает это сам) |
| 404 на весь сайт, файлы `_next/*` не находятся | нет `.nojekyll` (Jekyll отбрасывает каталоги с подчёркиванием); Pages не включён; опубликована не та ветка | `--nojekyll` в ручном варианте, шаг «Отключение Jekyll» в workflow; проверить Settings → Pages |
| Открывается старая версия | кэш браузера или кэширование Pages | Ctrl+F5; перезапустить workflow (Actions → Run workflow) |
| Сайт не обновился после push | workflow упал | вкладка Actions → журнал ошибок; локально повторить раздел 5 |
| Вместо инструмента открывается README репозитория | Pages отдаёт корень ветки с исходниками (Source = «Deploy from a branch» → `main`), где нет `index.html` — GitHub рендерит `README.md` как главную; инструмент ещё не публиковался | переключить Source: **GitHub Actions** (вариант А) или **gh-pages** (вариант Б); убедиться, что `.github/workflows/gh-pages.yml` загружен в репозиторий (скрытые папки часто теряются при загрузке через веб-интерфейс); запустить workflow и обновить страницу через Ctrl+F5 |

## 8. Бесплатные альтернативы, доступные из России

Состояние на ноябрь 2026. Для всех вариантов годится один и тот же
статический каталог `out/` (при публикации в подпапке — собранный с
`BASE_PATH`); ручной вариант раздела 3 воспроизводится почти везде.

| Сервис | Как публиковать | Free-лимиты | Из России | Примечания |
| --- | --- | --- | --- | --- |
| GitLab Pages | CI-конвейер `.gitlab-ci.yml` публикует каталог | ≈400 CI-минут/мес | доступен | та же схема, что в разделе 2; `BASE_PATH` задаётся при сборке |
| Codeberg Pages | каталог репозитория | бесплатно для свободных проектов | доступен | идёт миграция на новую версию Pages (v2 отключается до 31.12.2026) |
| Surge.sh | `npx --yes surge out https://<имя>.surge.sh` | практически без ограничений для статики | доступен | публикация одной командой, вход по e-mail |
| Neocities | веб-интерфейс или CLI | 1 ГБ места, 200 ГБ трафика/мес | доступен | подходит для учебных проектов |
| Hugging Face Spaces (Static) | загрузка файлов в Space | бесплатно | как правило доступен | адрес `<имя>.hf.space` |
| Yandex Object Storage | бакет в режиме «статический сайт» | бесплатные лимиты на хранилище и запросы | сервис РФ, стабильно | нужен платёжный аккаунт; HTTPS — со своим доменом через Certificate Manager |

Из российских провайдеров подойдут и бесплатные тарифы обычного хостинга
(например, SpaceWeb, Hostiman): статические файлы размещаются без
ограничений, регистрация по российскому телефону.

**Не рекомендуем в качестве основного из России** (на ноябрь 2026):
Netlify — встречаются блокировки аккаунтов; Vercel — жалобы на нестабильный
доступ `vercel.app` и кастомных доменов от российских провайдеров;
Cloudflare Pages — Cloudflare ограничивает пользователей из РФ, доступ
`pages.dev` нестабилен; Firebase Hosting и Google Cloud — не принимают новых
пользователей из РФ; Glitch — прекратил хостинг приложений в 2025. Через VPN
эти сервисы работают, но для учебного процесса полагаться на них не стоит.
