# Конструктор СКИБ — частное ТЗ на доработку v0.02.01

> Версия документа 0.02.01b-сх от 12.11.2026 · Статус: черновик для утверждения · Базовая версия инструмента: 0.01.10 · Родительский документ: ТЗ_Конструктор_СКИБ.md (разделы 3, 5, 6, 7, 11)
>
> Частное ТЗ описывает две функциональные подсистемы: **автонумерацию доменов безопасности** и **режим «Диаграммы последовательности» (ДП)** (редактор, валидатор, импорт/экспорт). Нумерация требований Ф-30…Ф-69 продолжает реестр родительского ТЗ (Ф-1…Ф-27); коды ошибок и предупреждений продолжают реестр раздела 6.5 (E-1xx…E-5xx, W-001…W-006 заняты).

## 1. Общие сведения

### 1.1. Цель доработки

ДАП (диаграмма архитектуры политики) описывает высокоуровневую архитектуру: потоки данных между доменами безопасности и требуемые уровни доверия. На ранних этапах проектирования архитектор может упустить отдельные аспекты взаимодействия и поведение доменов в динамике. Для этого в инструмент вводится режим **ДП (диаграмм последовательности)**, отражающий логику взаимодействия доменов по шагам. Набор ДП не обязан быть полным, но архитектору следует промоделировать хотя бы по одной ДП, специфичной для каждой цели безопасности или отражающей ключевой сценарий применения; так выявляются недоработки ДАП, которые исправляются в режиме валидации ДП.

Автонумерация доменов вводится как основа стабильных ссылок на домены: номер входит в полное название домена и используется для сопоставления при импорте/экспорте ДП, когда названия указаны кратко или не совпадают. Блоки стрелок структурируют сценарий: группа выделяет смысловой участок, цикл — повторяющиеся шаги, условный блок (if/else) — ветвление исходов (например, нормальное исполнение или реакция на нарушение политики безопасности).

### 1.2. Объём версии

В v0.02.01 реализуется:

1. автонумерация внутренних доменов безопасности (Ф-30…Ф-36);
2. переключатель режимов «Архитектура политики» / «Диаграммы последовательности» (Ф-37);
3. редактор ДП: несколько диаграмм, линии жизни, стрелки, блоки (группы, циклы, условные блоки), автонумерация стрелок, мини-навигатор, зум (Ф-38…Ф-48);
4. условные блоки стрелок (`if…else` PlantUML) и группы-циклы (`loop` PlantUML) (Ф-60…Ф-63, П-13, П-14);
5. валидация ДП с исправлением «добавить недостающие связи в ДАП» и списком неиспользуемых доменов (Ф-49…Ф-51);
6. импорт/экспорт ДП в форматах YAML (sequences.yaml, все ДП) и PlantUML (одна ДП); ДП включаются в state.yaml (Ф-52…Ф-57);
7. опция применения цветовой гаммы ДАП на канве ДП (Ф-59, П-11);
8. лимиты, сквозной сценарий приёмки, тесты, документация, версия 0.02.01 (Ф-58, раздел 9.1, разделы 9–10);
9. уточнения интерфейса по итогам приёмки (v0.02.01b): «Очистить ДП» с подтверждением, список ЦБ в левой панели с набрасыванием на канву, горячий фильтр доменов, пунктирные линии жизни до нижней границы экрана, содержательная мини-карта, поведение полей инспектора (Ф-64…Ф-69).

### 1.3. Вне объёма версии (отложено)

Перечисленное не входит в v0.02.01 и фиксируется как отложенные требования (раздел 11): удаление и добавление связей в ДП средствами режима валидации; ручная перестановка порядковых номеров доменов; блоки `alt/opt/par/critical/repeat/while` PlantUML как отдельные сущности (циклы `loop` и условные блоки `if…else` включены в объём — Ф-60…Ф-63); возвратные (пунктирные) стрелки как отдельный тип; автогенерация ДП из ДАП.

## 2. Термины и сокращения

| Термин | Определение |
| --- | --- |
| ДАП | Диаграмма архитектуры политики — текущий вид канвы (архитектура + цели/функции + расчёты). |
| ДП | Диаграмма последовательности — пошаговый сценарий взаимодействия доменов; в модели — `SequenceDiagram`. |
| ДБ | Домен безопасности; в модели — `Block` (внутренний или внешний). |
| ЦБ | Цель безопасности; ФБ — функция безопасности. |
| Линия жизни | Участник ДП: вертикальная полоса домена на канве ДП; домен участвует в одной ДП не более одного раза, но может участвовать в нескольких ДП. |
| Стрелка ДП | Горизонтальная стрелка между линиями жизни или self-стрелка (петля на своей линии жизни — процесс обработки информации); в модели — `SeqArrow`. |
| Self-стрелка | Стрелка домена в самого себя; на ДАП ей не соответствует связь — отдельная разрешающая политика безопасности не требуется. |
| Блок ДП | Именованный диапазон подряд идущих стрелок одной ДП; виды: группа (`group`), цикл (`loop`), условный блок (`if/else`); в модели — `SeqBlock` с полем `kind`. |
| Цикл | Блок-повторение «выполняется многократно»; PlantUML — `loop … end`. |
| Условный блок | Блок с ветвлением: ветка «то» (then) и ветка «иначе» (else), граница между ними — `elseFrom`; PlantUML — `if (…) then (…) … else (…) … end`. |
| Полное название домена | Имя домена с номером-префиксом: «01. Связь». Хранится в `Block.name` (решение П-2). |
| Матчинг | Сопоставление участника импортируемого файла с доменом ДАП по правилам раздела 7.3. |
| sequences.yaml | Файл описания всех ДП проекта (раздел 7.1). |

## 3. Принятые решения (по итогам проработки)

Решения П-1…П-14 фиксируют ответы на уточняющие вопросы и обязательны для реализации. Источник — проработка частного ТЗ от 12.11.2026.

| № | Вопрос | Решение |
| --- | --- | --- |
| П-1 | Какие домены нумеруются | Только домены внутри периметра (внутренние ДБ). Внешние системы номеров не получают и сопоставляются по названию. |
| П-2 | Хранение номера | Номер вшит в строку имени (`Block.name = "NN. Название"`). Ренумерация переписывает имена. Отдельного поля номера нет. |
| П-3 | Направление связи | Строгое: направленная стрелка — графическое представление политики безопасности, A→B и B→A — две разные политики. Стрелка ДП A→B требует на ДАП связь именно A→B. |
| П-4 | Применение исправлений валидации | Глобально, одной кнопкой. В v0.02.01 реализуется только «добавить недостающие связи в ДАП»; удаление/добавление связей в ДП из валидации не требуется. |
| П-5 | Подписи стрелок ДП | Необязательные, до 60 символов; обычно присутствуют; сохраняются при экспорте PlantUML/YAML, читаются и отображаются при импорте. |
| П-6 | Блоки стрелок | Блоки (группы, циклы, условные) покрывают только подряд идущие стрелки — один блок `group/loop/if…end` в PlantUML. Выход стрелки за границы диапазона — автоматический выход из блока. |
| П-7 | Порядок линий жизни | Перетаскивание по горизонтали в любой момент; стрелки следуют за линиями жизни. |
| П-8 | Форматы обмена | sequences.yaml — все ДП проекта одним файлом; PlantUML — одна выбранная ДП; ДП также хранятся внутри state.yaml. |
| П-9 | Матчинг при импорте | Порядок: id → номер «NN.» → точное имя → имя без префикса → подстрока. Неоднозначная подстрока — ошибка импорта. В PlantUML обрабатывается полное название `participant "…" as алиас`, а не сокращение. |
| П-10 | Инспектор режима ДП | Показывает выбранную линию жизни, стрелку или блок (группу, цикл, условный блок); без выбора — карточку самой ДП (переименование). |
| П-11 | Цветовая гамма ДП из ДАП | Опция (по умолчанию выключена): линии жизни окрашиваются по классу доверия домена, стрелки — по цвету домена-источника: из красных — красные, из жёлтых и зелёных — зелёные. Цвета производные, в модель данных и экспорт не пишутся. |
| П-12 | Состав участников ДП | Линии жизни любой ДП — произвольное подмножество ДБ и внешних систем ДАП, в том числе полное множество. Домен, отсутствующий на ДАП, добавить в ДП нельзя ни одним способом: набор доменов строится только из ДАП (5.3), импорт отклоняет несопоставленных участников (E-602, E-604), удаление домена снимает ссылки каскадом (5.6). Если доменов на ДАП более 24, полное множество в одну ДП не помещается — действует лимит линий жизни (Ф-58). |
| П-13 | Блоки стрелок ДП | Группа, цикл и условный блок — одна сущность `SeqBlock` (`kind: group/loop/cond`). Блок покрывает подряд идущие стрелки; блоки не пересекаются и не вкладываются; сквозная нумерация стрелок 1..N от блоков не зависит. Группам и циклам — палитра 8 цветов, условным блокам — нейтральная рамка без цвета. |
| П-14 | Условные блоки if/else | Экспорт — `if (условие) then (подпись) … else (подпись) … end`. В редакторе обе ветки обязательны и непусты; при импорте допустим `if` без `else` (ветка «то» покрывает все стрелки блока). `alt` остаётся вне подмножества (W-002, раздел 11). |

## 4. Автонумерация доменов безопасности

### 4.1. Инвариант нумерации (Ф-30)

1. Каждый внутренний домен имеет полное название вида `NN. Название`, где NN — порядковый номер: минимум два знака с ведущим нулём (01…99), от 100 — три знака; после номера — точка и пробел.
2. Номера внутренних доменов идут подряд без пропусков: 01, 02, …, K, где K — число внутренних доменов.
3. Порядок нумерации — порядок следования внутренних блоков в `architecture.blocks`; операции структуры не меняют относительный порядок, кроме добавления в конец.
4. Внешние системы не нумеруются и префиксов не имеют (П-1).
5. Инвариант восстанавливается после каждой операции, меняющей состав внутренних доменов или их имена: добавление, удаление, декомпозиция, импорт ДАП, правка имени.

### 4.2. Операции

| Операция | Поведение (Ф-31, Ф-32, Ф-33) |
| --- | --- |
| «+ Домен» | Внутренний домен добавляется в конец списка; получает очередной номер; итоговое имя — «NN. Новый домен». |
| Удаление внутреннего домена | После удаления все последующие внутренние домены перенумеровываются (префиксы переписываются, разрывов нет). |
| Декомпозиция | Дочерние домены добавляются в конец списка и нумеруются со следующего номера; затем инвариант восстанавливается полной перенумерацией. |
| Переименование | Инспектор редактирует название без префикса; префикс добавляется автоматически при сохранении. Если введён собственный префикс «NN. », он заменяется каноническим (нормализация). |
| Переименование внешней системы | Префикс «NN. » в начале введённого имени удаляется (внешние не нумеруются, Ф-35). |

### 4.3. Импорт ДАП и перенумерация (Ф-34)

При импорте architecture.yaml, PlantUML и state.yaml после разбора выполняется перенумерация внутренних блоков по порядку объявления:

- имя, уже начинающееся с назначаемого префикса «NN. », сохраняется как есть (домены с номерами не трогаются);
- имя без префикса получает его автоматически («домены без номеров автоматически получают номера»);
- двойных префиксов не возникает; нормализация применяется ко всем внутренним доменам.

### 4.4. Отображение (Ф-36)

Полное название (с номером) выводится всюду, где выводится домен: карточка на канве ДАП, инспектор, таблицы ДВБ и расширенного анализа, отчёты, линии жизни ДП, набор доменов, экспортируемые файлы. Отдельного переключателя показа номеров нет — номер неотделим от имени (П-2). Контрольные числа стоимости примеров (robot 486 / vessel 943) не меняются: стоимость не зависит от имён; домены примеров robot и vessel получают префиксы в демонстрационных файлах `src/samples/`.

## 5. Режим «Диаграммы последовательности»

### 5.1. Переключение режимов (Ф-37)

В верхней панели слева от кнопок работы с файлами размещается переключатель из двух кнопок: **«Архитектура политики»** (текущий вид, по умолчанию) и **«Диаграммы последовательности»**. Активная кнопка подсвечена; состояние режима — в viewStore, в историю и localStorage не пишется (как настройки вида). В режиме ДП: канва, панели и инспектор заменяются содержимым раздела 5.3–5.4; кнопки редактирования ДАП («+ Домен», «+ Внешняя система») отключаются; загрузка файлов ДАП, экспорт state, undo/redo, «Проверить» ДАП остаются доступными и действуют на общую модель.

### 5.2. Модель данных ДП (Ф-38, Ф-60)

```ts
/** Стрелка ДП. from == to допустимо (self-стрелка). */
interface SeqArrow { id: string; from: string; to: string; label?: string; }
/** Блок ДП: группа (group), цикл (loop) или условный блок (cond).
    Подряд идущие стрелки одной ДП; блоки не пересекаются и не вкладываются (П-13). */
interface SeqBlock {
  id: string;            // g-N
  kind: 'group' | 'loop' | 'cond';
  name: string;          // группа/цикл — имя; условный блок — условие
  color: string;         // группа/цикл — палитра; у cond не используется
  arrows: string[];      // подряд идущие стрелки (по порядку arrows)
  thenLabel?: string;    // cond: подпись ветки «то»
  elseLabel?: string;    // cond: подпись ветки «иначе»
  elseFrom?: string;     // cond: id первой стрелки ветки «иначе»; без него ветки else нет
}
/** Диаграмма последовательности. */
interface SequenceDiagram {
  id: string;            // seq-N
  name: string;          // до 60 символов, по умолчанию «Новая ДП»
  lifelines: string[];   // Block.id, без повторов; порядок = слева направо
  arrows: SeqArrow[];    // порядок массива = вертикальный порядок = нумерация 1..N
  blocks: SeqBlock[];
}
/** Project дополняется необязательным полем (обратная совместимость): */
sequences?: SequenceDiagram[];
```

Правила целостности:

1. линии жизни любой ДП — произвольное подмножество доменов ДАП (внутренних и внешних), включая вариант полного множества (П-12); домен, отсутствующий на ДАП, добавить нельзя: набор доменов (5.3) строится только из доменов ДАП, импорт отклоняет несопоставленных участников (7.3, E-602/E-604), ссылки на удалённые домены снимаются каскадом (5.6);
2. каждый домен встречается в `lifelines` одной ДП не более одного раза; участвовать в нескольких ДП разрешено;
3. `from`/`to` каждой стрелки входят в `lifelines` своей ДП;
4. вертикальная позиция стрелки определяется её позицией в `arrows` — координаты Y не хранятся; стрелки отображаются равномерно, пересечения исключены;
5. `blocks[]` покрывают подряд идущие стрелки текущей ДП (по порядку `arrows`); блоки не пересекаются и не вкладываются (П-13); у условного блока ветка «то» — стрелки до `elseFrom`, ветка «иначе» — от `elseFrom` до конца блока; в редакторе обе ветки создаются непустыми, при импорте допустим `if` без `else` (П-14); группа — не менее двух стрелок, цикл — не менее одной;
6. self-стрелкам (from == to) на ДАП не требуется соответствие (см. 6.1).

### 5.3. Левая панель и правая панель режима ДП

**Левая панель (Ф-39, Ф-64, Ф-65):** список ДП (имя, счётчики «линий жизни/стрелок»), выбор — переключение диаграмм; кнопка «Создать» (имя уникализируется: «Новая ДП», «Новая ДП 2», …); «Очистить ДП» с подтверждением (в диалоге указываются имя и счётчики линий жизни/стрелок/блоков; очистка удаляет содержимое ДП целиком — одна операция истории) (Ф-64); «Удалить ДП» с подтверждением (в диалоге указывается имя и число удаляемых стрелок); **список целей безопасности (ЦБ)** (Ф-65): карточки целей ДАП, перетаскиваемые на канву — при отсутствии ДП создаётся ДП с именем ЦБ и линиями жизни критичных для неё доменов (домены размещения обязательных механизмов цели), при наличии текущей ДП её линии жизни пополняются критичными доменами ЦБ; можно набросить несколько ЦБ подряд; каждая операция — один шаг истории (Ctrl+Z отменяет целиком); блок импорта/экспорта: «Импорт YAML» (sequences.yaml, все ДП), «Импорт PlantUML» (одна ДП), «Экспорт YAML» (все ДП), «Экспорт PlantUML» (выбранная ДП). Ширина панели регулируется перетаскиванием.

**Правая панель (Ф-40, Ф-41, Ф-48):** три блока, высоты регулируются разделителями (как блоки расчёта и статуса системы в ДАП), ширина панели регулируется:

1. **Набор доменов** — карточки всех доменов ДАП: внутренние с полным названием («01. Связь»), внешние с пометкой «внешняя»; горячий фильтр по подстроке названия (без учёта регистра) для быстрого поиска нужного домена (Ф-66). Перетаскивание карточки на канву создаёт линию жизни. Домен, уже включённый в выбранную ДП, помечается и повторно не добавляется (drag блокируется, карточка приглушена).
2. **Инспектор** (П-10):
   - ничего не выбрано — карточка ДП: имя (редактируемое поле), счётчики; все текстовые поля инспектора обновляются при смене выбранного объекта и применяются по Enter или потере фокуса (Ф-67);
   - выбрана линия жизни: полное название домена, пометка «внутренний/внешняя», кнопка «Убрать из ДП» (удаляет линию жизни и её стрелки, блоки чистятся; одна операция истории);
   - выбрана стрелка: номер, направление («A → B»), подпись (поле до 60 символов), блок (имя + «Покинуть блок»), кнопка «Удалить стрелку»;
   - выбрана группа или цикл (клик по заголовку блока на канве): имя (поле), цвет (палитра из 8 фиксированных цветов), число стрелок, «Разгруппировать», «Удалить блок со стрелками» (с подтверждением);
   - выбран условный блок: условие (поле), подписи веток «то»/«иначе» (поля), число стрелок каждой ветки, «Разгруппировать», «Удалить блок со стрелками» (с подтверждением).
3. **Валидация** — кнопка «Проверить ДП» и таблица результатов (раздел 6); кнопка «Добавить недостающие связи в ДАП» появляется при наличии расхождений.

### 5.4. Канва ДП

**Линии жизни (Ф-38, П-7, Ф-68):** заголовок с полным названием домена (у внешних систем — дополнительно бейдж «внешняя») и вертикальная пунктирная линия (как на UML-диаграммах), продолжающаяся до нижней границы видимой области канвы независимо от числа стрелок (Ф-68); зона жеста создания стрелки следует за линией на всей её длине — стрелку можно создавать в любой точке линии жизни. Перетаскивание заголовка по горизонтали меняет порядок линий жизни в любой момент; стрелки следуют за линиями жизни. Порядок сохраняется в `lifelines`. Перетаскивание не пишется в историю (как перемещение доменов в ДАП), но сохраняется автосохранением.

**Стрелки (Ф-42, Ф-43, Ф-44, Ф-45):**

- горизонтальная стрелка между линиями жизни создаётся перетаскиванием от линии жизни-источника к линии жизни-приёмнику; направленность любая — слева направо и справа налево (strict-режим портов: направление определяет тип порта, как в ДАП v0.01.08);
- self-стрелка создаётся перетаскиванием линии жизни на себя; отображается петлёй справа от полосы линии жизни;
- подпись (необязательная) выводится над стрелкой; номер-бейдж — у начала стрелки;
- перетаскивание стрелки по вертикали меняет её позицию в порядке: стрелка вставляется перед/после соседней по вертикальной позиции; автонумерация 1..N пересчитывается сразу;
- удаление — клавишей Delete или из инспектора.

**Блоки (Ф-46, Ф-61, П-6, П-13, П-14):** выделение стрелок (клик с Shift/Ctrl) и команды «Сгруппировать», «Цикл», «Условный блок», активные только для подряд идущих стрелок (иначе — подсказка). Группа — цветная полоса-скобка с подписью имени (имя по умолчанию «Группа N», цвет — первый свободный из палитры); цикл — рамка с заголовком «Цикл: имя» и цветом палитры; условный блок — нейтральная рамка с заголовком «Если: условие», горизонтальным разделителем между ветками и подписями веток «то»/«иначе»; создаётся в диалоге: условие, подписи веток, граница else (номер первой стрелки ветки «иначе»), обе ветки непусты. Правила:

1. внутри блока стрелки переставляются свободно (в условном блоке — в пределах своей ветки), блок следует за ними;
2. при переносе стрелки за границу блока она автоматически покидает его; опустевшая ветка «иначе» оставляет условный блок без else (модель допускает), опустевшая ветка «то» распускает блок; группа, сжавшаяся до одной стрелки, распускается; цикл из одной стрелки сохраняется;
3. правка имени/цвета/условия/подписей веток — в инспекторе блока; «Разгруппировать» — без подтверждения; «Удалить блок со стрелками» — с подтверждением.

**Мини-навигатор и зум (Ф-47, Ф-69):** как в ДАП — React Flow MiniMap в левом нижнем углу центральной части и контролы зума (+, −, центрирование/вписать); мини-карта ДП показывает содержимое диаграммы — заголовки линий жизни и стрелки, а не пустой прямоугольник (Ф-69).

**Пустая ДП:** в центре канвы подсказка «Перетащите домены из набора справа, чтобы создать линии жизни».

### 5.5. Цветовая гамма из ДАП (опция) (Ф-59, П-11)

В режиме ДП в верхней панели рядом с переключателем режимов размещается опция **«Цвета из ДАП»** (по умолчанию выключена). Состояние опции — в viewStore: между сеансами не сохраняется и сбрасывается при перезагрузке страницы, как все настройки вида; переключение режимов состояние опции сохраняет в рамках сеанса.

При включении опции канва ДП окрашивается по модели доверия ДАП (`computeTrust`, раздел 3.5 родительского ТЗ) без изменения модели данных:

1. **линии жизни** — цветом класса доверия домена, как заливка домена на ДАП: НДБ — красный, ДДБ — зелёный, ДДБПЦД — жёлтый; внешние системы — недоверенная красный, доверенная зелёный;
2. **все стрелки ДП** (включая self-стрелки) — цветом домена-источника: из красных доменов (НДБ, недоверенная внешняя) все исходящие стрелки красные; из жёлтых и зелёных (ДДБПЦД, ДДБ, доверенная внешняя) — зелёные. Правило совпадает с окраской стрелок ДАП по целостности потока (у ДДБПЦД жёлтая заливка, но исходящие стрелки зелёные — источник доверенный);
3. **группы** сохраняют пользовательские цвета палитры — окраска групп и их подписей опцией не меняется;
4. цвета производные: не хранятся в Project, пересчитываются мгновенно при любом изменении модели ДАП (размещения функций, forceTrusted, trusted внешних систем) и при переключении опции; в экспорт PlantUML/YAML/state цвета не входят.

При выключенной опции канва ДП использует нейтральные цвета (текущие).

| Событие | Поведение |

| Импорт architecture.yaml / PlantUML / state.yaml (замена ДАП) | Каскад по всем ДП; при фактических удалениях — сводное предупреждение W-009 в панель валидации. |

## 6. Валидация ДП

### 6.1. Правила (Ф-49, Ф-51)

Кнопка «Проверить ДП» анализирует **все ДП проекта**:

1. Для каждой стрелки ДП (кроме self) проверяется наличие на ДАП связи `from → to` **с учётом направления** (П-3). Отсутствие — расхождение, строка ошибки E-601.
2. Секция «Неиспользуемые домены» (Ф-51): домены и внешние системы ДАП, не входящие ни в одну линию жизни ни одной ДП, выводятся строками-предупреждениями W-008 (для внешних систем — пометка).

Использование произвольного подмножества доменов ДАП — норма (П-12), поэтому W-008 носит информационный характер: оно не считается расхождением и само по себе не активирует кнопку исправления (6.3).

Режим валидации не блокирует редактирование; результат обновляется при повторном нажатии «Проверить ДП».

### 6.2. Таблица результатов

Колонки: Код | ДП | Стрелка (номер и «A → B») | Сообщение. Секции: «Расхождения связей» (E-601) и «Неиспользуемые домены» (W-008, Ф-51). Пустой результат — «Расхождений не найдено» с зелёной индикацией.

### 6.3. Исправление «Добавить недостающие связи в ДАП» (Ф-50, П-4)

Кнопка появляется под таблицей при наличии строк E-601 и выполняет **глобальное** применение ко всем расхождениям сразу:

1. для каждой строки в `architecture.edges` добавляется связь `from → to` с направлением из стрелки ДП; подписи стрелок ДП **не переносятся**; цвет новой связи определяется нотацией ДАП как у остальных связей (по модели доверия);
2. дубликаты существующих связей пропускаются; применение атомарно — при нехватке лимита MAX_EDGES операция целиком отклоняется с сообщением;
3. операция записывается в историю одним шагом (Ctrl+Z отменяет все добавленные связи);
4. после применения валидация перезапускается автоматически.

Удаление расхождящих связей в ДП и добавление связей в ДП из режима валидации в v0.02.01 не реализуются (П-4, раздел 11).

## 7. Импорт и экспорт ДП

### 7.1. Формат sequences.yaml (Ф-52, Ф-63, П-8)

```yaml
version: 1
domains:                 # справочник полных названий (экспорт); для человека
  dom-1: 01. Связь
  dom-2: 02. Контроль подлинности
  ext-1: Сервер обновлений (внешняя)
sequences:
  - id: seq-1
    name: Обновление прошивки
    lifelines: [dom-1, dom-2, ext-1]
    arrows:
      - id: a-1
        from: dom-1
        to: dom-2
        label: запрос на обновление
      - id: a-2
        from: ext-1
        to: dom-2
        label: передача пакета образа
      - id: a-3
        from: dom-2
        to: dom-2
        label: проверка подписи
      - id: a-4
        from: dom-2
        to: dom-1
        label: подтверждение установки
      - id: a-5
        from: dom-2
        to: ext-1
        label: тревога: нарушение подлинности
    blocks:
      - id: g-1
        kind: loop
        name: до получения полного образа
        color: '#F9A825'
        arrows: [a-1, a-2]
      - id: g-2
        kind: cond
        name: подлинность образа подтверждена
        thenLabel: нормальное обновление
        elseLabel: нарушение подлинности
        elseFrom: a-5
        arrows: [a-3, a-4, a-5]
```

- `version` равен FILE_VERSION (1); `domains` — необязательный справочник «id → полное название», экспортируется для всех доменов, встречающихся в файле (требование «при экспорте указывать полное название вместе с номером»);
- `lifelines`, `from`, `to`, `blocks[].arrows` при импорте могут быть заданы: идентификатором домена, полным названием с номером, точным названием без номера или частью названия — сопоставление по разделу 7.3;
- `color` — hex `#RRGGBB`; при импорте принимается любой корректный hex, при экспорте выводится цвет группы/цикла (у условных блоков цвета нет);
- `blocks[]` — блоки ДП; `kind` — `group|loop|cond`; у cond поля `thenLabel`/`elseLabel`/`elseFrom` необязательны (без `elseFrom` — `if` без ветки «иначе»);
- ошибки: некорректный YAML — E-001; несоответствие схеме — E-002; неизвестные поля — W-001; ссылка на необъявленную стрелку в блоке или на участника вне `lifelines` — E-604; блок не из подряд идущих стрелок, пересекающийся с другим блоком или с некорректной границей ветки «иначе» — E-605.

Импорт YAML **заменяет все ДП проекта** данными файла (одна операция истории) — формат уровня проекта.

### 7.2. Подмножество PlantUML для ДП (Ф-53, Ф-62, П-8, П-9)

Экспорт одной ДП (имя файла — `<имя ДП>.puml`):

```plantuml
@startuml
autonumber
participant "01. Связь" as dom-1
participant "02. Контроль подлинности" as dom-2
participant "Сервер обновлений (внешняя)" as ext-1 <<external>>

loop до получения полного образа #F9A825
dom-1 -> dom-2 : запрос на обновление
ext-1 -> dom-2 : передача пакета образа
end
if (подлинность образа подтверждена) then (нормальное обновление)
dom-2 -> dom-2 : проверка подписи
dom-2 -> dom-1 : подтверждение установки
else (нарушение подлинности)
dom-2 -> ext-1 : тревога: нарушение подлинности
end
@enduml
```

- участник: `participant` (для всех доменов; внешние системы — со стереотипом `<<external>>`); алиас — идентификатор домена; в кавычках — полное название с номером;
- стрелка: `A -> B : подпись`; self — `A -> A : подпись`; `autonumber` — включается в экспорт (нумерация PlantUML совпадает с нашей), при импорте игнорируется;
- группа: `group <имя> [#цвет]` … `end`; цикл: `loop <имя> [#цвет]` … `end`; условный блок: `if (<условие>) then (<подпись «то»>)` … `else (<подпись «иначе»>)` … `end` — рамка блока выводится на месте его первой стрелки и охватывает ровно его стрелки; при `if` без `else` секция `else` не выводится;

Импорт (подмножество):

| Конструкция | Обработка |
| --- | --- |
| `participant "Имя" as алиас`, `participant "Имя"`, `participant алиас`, `actor …` | Объявление участника; сопоставление «Имя» (в кавычках) с ДАП по разделу 7.3; алиас — ключ для стрелок; дубликат алиаса/имени — E-603 |
| `A -> B : text`, `A ->> B`, `A --> B` | Стрелка; тип линии (сплошная/пунктир) не различается; `text` — необязательная подпись |
| `A <- B`, `A <-- B` | Стрелка с инвертированным направлением (B → A) |
| `group <имя> [#цвет]` … `end`, `loop <имя> [#цвет]` … `end` | Блок (группа/цикл) подряд идущих стрелок; вложенные блочные конструкции — W-002, внутренние заголовки игнорируются, стрелки относятся к внешнему блоку |
| `if (<условие>) then (<подпись>)` … [`else (<подпись>)`] … `end` | Условный блок (kind=cond): условие → `name`, подписи → `thenLabel`/`elseLabel`, первая стрелка после `else` → `elseFrom`; `else`/`end` без открытого блока — E-609 |
| `autonumber`, `title`, `skinparam`, `scale`, `hide/show`, `caption`, `legend/footer/header`, `activate/deactivate/destroy`, `== … ==`, комментарии `'` | Игнорируются молча |
| `note`, `box`, `!…`, прочее | W-002 «конструкция вне подмножества» (однократно на конструкцию); блоки `note`/`box` пропускаются целиком |
| строки вне `@startuml…@enduml` | Игнорируются; отсутствие пары — E-608 |
| нераспознанная строка | E-607 |

### 7.3. Правила сопоставления доменов (матчинг) (Ф-54, П-9)

Вход — строка S (полное название участника PlantUML, значение `lifelines`/ссылки YAML или запись справочника `domains`). Порядок шагов; первый успешный — результат:

1. **id**: S совпадает с идентификатором блока ДАП (`dom-N`, `ext-N`) → матч.
2. **Номер**: S начинается с `NN. ` (NN — целое) → среди внутренних доменов ищется домен с текущим номером NN. Найден: совпадает и остаток названия — точный матч; не совпадает — матч по номеру с предупреждением W-007 («название в файле и в проекте различаются — принято по номеру»). Внешние системы по номеру не матчатся.
3. **Точное имя**: S совпадает с полным названием домена или с названием без префикса → матч.
4. **Подстрока**: S (без учёта регистра) содержится в названии домена → если кандидат ровно один — матч; несколько — ошибка E-606; ни одного — шаг 5.
5. Не сопоставлен — ошибка E-602 «участник … не сопоставлен с доменом ДАП».

Для PlantUML ключ стрелки (алиас или имя) сначала резолвится по объявлениям участников, затем участник сопоставляется с ДАП по шагам выше. Любая ошибка импорта блокирует применение файла целиком (Ф-6).

### 7.4. state.yaml (Ф-55)

В state.yaml добавляется необязательная секция `sequences:` — массив в формате раздела 7.1 (без `version` и `domains`; ссылки — идентификаторы доменов той же архитектуры). Отсутствие секции — норма (файлы v0.01.x). Ссылка на домен, отсутствующий в `architecture` этого же файла, — E-604. Файл v0.02.01, открытый в старой версии инструмента, даёт W-001 «неизвестное поле sequences» — обратная совместимость односторонняя, ДП в старой версии теряются.

## 8. Лимиты (Ф-58)

| Параметр | Значение |
| --- | --- |
| ДП на проект | не более 20 |
| Линий жизни в ДП | не более 24 |
| Стрелок в ДП | не более 100 |
| Блоков (групп, циклов, условных) в ДП | не более 10 |
| Имя ДП, имя блока, условие и подписи веток, подпись стрелки | до 60 символов |

Превышение — операция не применяется, выводится сообщение (toast). Строки сущностей ДП соответствуют ID_PATTERN, кроме стрелок/блоков — `a-N`, `g-N`. Лимит линий жизни действует и на вариант полного множества (П-12): пока доменов на ДАП не более 24, все они помещаются в одну ДП; при большем числе в ДП включается подмножество.

## 9. Требования к тестам

### 9.1. Сквозной сценарий приёмки (ДАП «Безэкипажное судно-доставщик»)

База — ДАП образца 2 «Безэкипажное судно-доставщик» (22 блока: 18 внутренних, 4 внешние). Генерируются две ДП; каждая стрелка (кроме self) соответствует связи ДАП с точным направлением (П-3), участники — все релевантные ДБ сценария (П-12):

1. **seq-1 «Удалённое обновление прошивки»** — 9 линий жизни, 13 стрелок: Береговой пост (СУДС), Радиоэфир, 10. Радиосвязь, 06. Подсистема OTA-обновления, 15. Верификация и применение обновления прошивки, 04. Навигационный вычислитель, 07. Бортовой ИИ, 12. Контроль миссии, 17. События безопасности. Цикл «до получения полного образа» (передача и приём пакетов обновления), затем условный блок «подлинность прошивки подтверждена»: ветка «нормальное обновление» — применение верифицированной прошивки, ввод её в работу на навигационном вычислителе и обновление моделей ИИ; ветка «нарушение подлинности» — отклонение обновления, регистрация события безопасности и передача тревоги береговому посту.
2. **seq-2 «Выполнение новой миссии»** — 12 линий жизни, 21 стрелка: Береговой пост (СУДС), Радиоэфир, 10. Радиосвязь, Оператор шлюза, 12. Контроль миссии, 04. Навигационный вычислитель, 13. Контроль положения, 14. Аварийный уход от столкновения, 09. Контроль груза и выгрузки, 16. Выполнение критичных команд, 17. События безопасности, 18. Блокировка движения. Приём и контроль подлинности миссии, цикл «контроль обстановки по ходу миссии» (данные курса/позиции, контроль целостности), затем условный блок «критических нарушений в системе управления не выявлено»: ветка «нормальное выполнение миссии» — маршрутный лист, заявка и разрешение шлюзования, отчёты о статусе груза и миссии; ветка «аварийная остановка» — признак критического нарушения, экстренное торможение, регистрация события безопасности, критичная команда и блокировка движения, тревога береговому посту.

Процедура приёмки: генерация ДП → проверка отображения (линии жизни, номера стрелок, рамки циклов и ветвления с разделителем веток) → экспорт sequences.yaml (обе ДП) и PlantUML (каждая ДП отдельно) и state.yaml с секцией `sequences` → контроль экспортированных файлов (схема, полные названия с номерами, состав блоков) → импорт каждого файла → сравнение результата с оригиналом (линии жизни и их порядок, стрелки с подписями и направлениями, блоки всех видов с ветками — полное совпадение) → «Проверить ДП» без расхождений. Образцы ДП включаются в `src/samples/` при реализации v0.02.01.

### 9.2. Unit-тесты (Vitest, кейсы T-S-01…)

v0.02.01b добавляет кейсы: «Очистить ДП» (Ф-64) — содержимое удаляется одним шагом истории, пустая ДП не создаёт шага; имя ДП при создании задаётся явно и уникализируется; ЦБ (Ф-65) — создание ДП по имени ЦБ с критичными доменами, добавление критичных доменов в существующую ДП (дубликаты пропускаются, лимит линий жизни соблюдается), один шаг истории.

1. перенумерация: добавление, удаление в середине списка, декомпозиция; нормализация при переименовании; ввод имени с чужим префиксом; внешние системы без номеров (Ф-30…Ф-35);
2. формат номера: 01…99 с ведущим нулём, 100+ без него;
3. матчинг: id, номер (точный и с W-007), точное имя, имя без префикса, однозначная подстрока, E-606, E-602 (Ф-54);
4. парсер PlantUML ДП: `participant … as`, `actor`, стрелки всех поддержанных видов и реверсы, self, `group…end`, `loop…end`, `if…then…else…end` (с else и без), игнорируемые конструкции, W-002, E-603, E-607, E-608, E-609, вложенные блоки — W-002;
5. сериализация PlantUML ДП: полное название с номером, алиасы-идентификаторы, стереотип внешней, `group #цвет`, `loop #цвет`, `if…then…else…end`, `autonumber`; круговая проверка экспорт → импорт (включая блоки);
6. sequences.yaml: схема, справочник `domains`, блоки всех видов (`kind`, `thenLabel`/`elseLabel`/`elseFrom`), E-604, E-605, W-001; круговая проверка;
7. state.yaml: с `sequences` и без; E-604 по доменам той же архитектуры;
8. валидатор ДП: E-601 с учётом строгого направления (реверс — расхождение), self не проверяется, W-008 по всем ДП;
9. «Добавить недостающие связи в ДАП»: направление, отсутствие подписи, дубликаты, атомарность при MAX_EDGES, одна операция истории;
10. каскады: `deleteDomain`, замена ДАП (W-009), `loadState`, `resetProject`;
11. блоки: создание из подряд идущих, отказ для несмежных, автоматический выход стрелки из блока, роспуск группы при одной стрелке, сохранение цикла из одной стрелки; условный блок — непустые ветки в редакторе, if без else при импорте, перенос стрелки через границу ветки;
12. лимиты Ф-58; попытка включить в одну ДП все домены ДАП при их числе больше 24 упирается в лимит линий жизни (П-12);
13. окраска из ДАП (Ф-59, П-11): цвета линий жизни по классу доверия (НДБ — красный, ДДБ — зелёный, ДДБПЦД — жёлтый), цвета стрелок по источнику (из красных — красные, из жёлтых и зелёных — зелёные), self-стрелки, доверенные и недоверенные внешние, группы не перекрашиваются, цвет не записывается в модель и экспорт, сброс опции при перезагрузке страницы.

### 9.3. E2E (Playwright, кейсы T-U-01…)

Переключение режимов; создание и удаление ДП (подтверждение); drag домена из набора → линия жизни (набор содержит ровно домены ДАП — П-12; при их числе ≤ 24 допустимо полное множество); добавление стрелок обеих направленностей и self; перенос стрелки — автонумерация обновилась; блоки: группа и цикл (создание из подряд идущих, правка имени/цвета, разгруппировка, удаление со стрелками), условный блок (диалог с условием, подписями веток и границей else; разделитель веток на канве; правка в инспекторе); валидация: расхождение → «Добавить недостающие связи в ДАП» → без расхождений; секция неиспользуемых доменов; импорт/экспорт sequences.yaml и PlantUML (круговая); сквозной сценарий 9.1: генерация → отображение → экспорт → контроль файлов → импорт → сравнение с оригиналом; удаление домена в ДАП — каскад и перенумерация названий в ДП; мини-навигатор и зум присутствуют; опция «Цвета из ДАП»: включение перекрашивает линии жизни и стрелки, выключение возвращает нейтральные; регрессия ДАП не сломана.

## 12. Приёмочные критерии

1. Инвариант нумерации выполняется после любой операции; сквозной сценарий раздела 9.1 проходит.
2. Режим ДП полноценно работает без ДП (пустые состояния) и с несколькими ДП; переключение режимов не теряет данных. Линии жизни любой ДП — подмножество доменов ДАП, включая полное множество; домен вне ДАП не добавляется ни перетаскиванием, ни импортом (П-12).
3. Валидация ДП находит все расхождения направлений; кнопка исправления добавляет ровно недостающие связи и не меняет подписи и цвета ДАП.
4. Экспортированные sequences.yaml и PlantUML загружаются обратно без потерь (круговые тесты); импорт с краткими названиями (номер/часть) находит домены по разделу 7.3.
5. `make check` зелёный; документация и CHANGELOG обновлены; версия 0.02.01 во всех точках синхронизации.
6. Опция «Цвета из ДАП» перекрашивает линии жизни и все стрелки ДП по модели доверия (из красных доменов — красные стрелки, из жёлтых и зелёных — зелёные); выключение возвращает нейтральный вид; группы и экспортируемые файлы не меняются.
7. Условные блоки и циклы создаются, отображаются и переносятся через экспорт/импорт без потерь (круговые проверки seq-1 и seq-2); разорванные, пересекающиеся и вложенные блоки отклоняются (E-605, E-609, W-002).
8. Уточнения приёмки (v0.02.01b, Ф-64…Ф-69): демо-комплект «Судно» показывает обе образцовые ДП; линии жизни — пунктир до нижней границы канвы, жест стрелки работает по всей длине; мини-карта отражает линии жизни и стрелки; «Очистить ДП» работает после подтверждения (один шаг истории); фильтр «Набора доменов» отбирает карточки по подстроке; набрасывание ЦБ на пустую канву создаёт ДП с именем ЦБ и критичными доменами, на текущую ДП — пополняет её линии жизни; поля инспектора обновляются при смене выбора и применяются по Enter.
