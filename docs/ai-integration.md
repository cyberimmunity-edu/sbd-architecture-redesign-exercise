# Интеграция с ИИ-агентами — справочник по инструменту

> Версия документа: 0.03.01b · Аудитория: LLM-агенты и разработчики интеграций ·
> Родительские документы: ТЗ_Конструктор_СКИБ.md, docs/dev-roadmap.md, AGENTS.md

Инструмент «Моделирование СКИБ» — настольное приложение (static export, без сервера),
вся логика живёт в чистом TypeScript-движке (`src/engine`, `src/io`). Для ИИ-агентов
движок доступен **без браузера и без сборки** — через CLI `skib`. Модель хранится
одним файлом `state.yaml` («модель-в-коде»), поэтому агент работает с ней как с текстом:
читает, правит, проверяет, повторяет цикл до чистой валидации.

---

## 1. Онтология (минимум для работы с моделью)

- **ДАП** — архитектурная схема целевой системы: домены безопасности (ДБ), внешние
  (смежные) системы, стрелки потоков данных, логические группы (ЛГ), рамка периметра.
- **Уровни доверия ДБ** (вычисляются, не задаются): **НДБ** — недоверенный (нет критичных
  функций, K = 0.1); **ДДБ** — доверенный (есть критичная функция, все входы зелёные,
  K = 5); **ДДБПЦД** — доверенный домен, повышающий целостность данных (в него входит
  красная стрелка, K = 10). Критичная функция — связанная с целью безопасности
  (`implements`), любой вес. Внутренний домен может быть введён в ДВБ принудительно
  (`forceTrusted`) — например, доверенный датчик без собственной ФБ, необходимый
  функциям безопасности других доменов; у такого домена с красным входом проверка
  «Проверить» выдаёт W-013 (обоснуйте признак или смоделируйте контроль ФБ).
- **Цвет стрелки**: зелёный — источник доверенный (ДДБ/ДДБПЦД/доверенная внешняя);
  красный — низкоцелостный поток.
- **ЛГ (логические группы)** — рамки вокруг ДБ: имя, цвет из палитры `LG_COLORS`
  (красный, жёлтый, зелёный зарезервированы под уровни доверия), вложенность до 3,
  свёртывание. ЛГ не влияет на расчёты — только на читаемость.
- **ДП (диаграммы последовательности)** — секция `sequences`: линии жизни = id ДБ,
  стрелки, блоки group/loop/cond. Валидатор сверяет стрелки ДП со связями ДАП (E-601).
- **Модель стоимости** (раздел 7.1 ТЗ): `C_домена = ceil(C_блока × S × M × K)`,
  где S — сумма стоимостей размещённых функций, M — множитель связности
  (E = (E_вх + E_исх)/2, при E < 2 → 1), K — коэффициент доверия.
  `C_системы` — сумма по внутренним доменам; внешние системы не считаются.
- **Ключевая экономика архитектуры**: стоимость растёт с размером доверенной зоны
  (ДДБ/ДДБПЦД, K = 5–10) и с плотностью границы доверия. Советчик предлагает
  перестроения с точной оценкой экономии (см. §4).

## 2. Формат модели

- **state.yaml v1** — самодостаточный файл: архитектура + цели/функции + размещения
  (+ опционально `sequences` и `groups`). JSON-схема: `docs/state.schema.json`
  (команда `skib schema`). Схема описывает типы и лимиты; уникальность и ссылки
  проверяет семантическая валидация.
- Идентификаторы: `^[a-z][a-z0-9-]{0,63}$`. Лимиты: ≤200 доменов, ≤500 стрелок,
  ≤20 ДП, ≤24 линий жизни, ≤100 стрелок ДП, ≤10 блоков/ДП, ≤20 ЛГ.
- Поле `position` опционально — агент может править структуру без координат.
- **Канонический экспорт**: `skib export --format state` разбирает и собирает модель
  заново (стабильный порядок полей, без неизвестных ключей). Round-trip
  гарантируется тестами (`tests/unit/cli.test.ts`).

## 3. CLI — команды и цикл работы агента

Запуск: `node cli/skib.mjs <команда> <state.yaml> [опции]` (Node ≥ 24; на Node 22.12+
добавьте флаг `--experimental-strip-types`). Вывод — JSON в stdout; `--pretty` — с отступами.
Коды возврата: 0 — успех, 1 — ошибки файла, 2 — ошибка использования.

| Команда | Назначение | Ключевые поля вывода |
|---|---|---|
| `validate <файл>` | структура и ссылки state.yaml | `errors[].{code,message,path,hint}`, `summary.systemCost` |
| `check <файл>` | семантика «Проверить»: трассировка цель→функция→домен, W-013 | `errors` (E-501/E-502), `warnings` (W-006, W-013) |
| `metrics <файл>` | снимок метрик | `metrics.{systemCost, dvb, composition, goals, sequences, groups, advice}` |
| `advice <файл>` | советы с оценкой экономии | `advice[].{kind, blocks, functions, deltaC, params}` |
| `export <файл>` `--format state\|plantuml [--out путь]` | канонический экспорт | `content` или `out` |
| `schema` | JSON-схема state.yaml v1 | `schema` |
| `version` | версия движка | `version` |

Стандартный цикл агента («изменил → проверил → исправил»):

```bash
node cli/skib.mjs validate model.yaml        # код 1? читаем errors[].hint
# правим model.yaml по hint (поле path указывает место)
node cli/skib.mjs validate model.yaml        # до кода 0
node cli/skib.mjs metrics model.yaml         # проверяем экономику изменений
```

Каждая ошибка содержит `hint` — машинную подсказку «как исправить» (таблица
`HINTS` в `src/io/errors.ts`, покрыта тестом на полноту для всех кодов E-/W-).

## 4. Советы советчика (каталог С1–С9)

Советы — эвристики улучшения с **точной** оценкой экономии: кандидат «что-если»
пересчитывается `recalcCosts` на клоне модели, `deltaC` = разность C_системы.
Автоприменения нет — решение за человеком. Кандидатную модель можно получить
функцией `adviceCandidate(project, advice)` (`src/engine/advisor.ts`).

- `goal-coverage` (С6) — цель не покрыта размещёнными функциями;
- `unlinked-function` (С5) — функция без связей с целями занимает домен;
- `empty-domain` / `isolated-domain` (С4) — структурные проблемы;
- `ddbpcd-split` (С1) — вынос **некритичных** функций из ДДБПЦД в НДБ; если
  некритичных нет, интерфейсный домен уже минимальный и такой совет не даётся;
- `ddb-regroup` (С2) — вынос некритичных функций из ДДБ в НДБ (остаток остаётся ДДБ);
- `trusted-split` (С8, v0.03.01b) — «валидатор + исполнитель»: часть функций
  переезжает в новый доверенный домен с зелёным входом от валидатора (K: 10 → 5);
- `gateway-split` (С9, v0.03.01b) — «шлюз с функциями»: валидатор выносится в
  новый ДДБПЦД, красные стрелки перенаправляются ему, исполнитель остаётся;
- `filter-domain` (С3) — дешёвый посредник для низкоцелостных входов; допущения
  кандидата раскрыты в `params` (`mediatorCost = 1`, `mediatorForceTrusted = 1`);
- `cost-leader` (С7) — навигационный: домен-лидер стоимости.

**Вариантный перебор (v0.03.01b)**: для каждого доверенного домена перебираются
варианты разбиения на две части (все подмножества функций при n ≤ 10, иначе
эвристическое семейство), каждому домену выдаётся до **трёх** лучших вариантов
с положительной deltaC (`MAX_VARIANTS_PER_DOMAIN`). Варианты одного домена —
альтернативы, не сумма: экономику каждого подтверждает независимый пересчёт
кандидата. Выбор варианта (в том числе какая часть — валидатор) — модельное
решение студента.

Гарантии (закреплены тестами `tests/unit/advisor.test.ts`): детерминизм, сортировка
по экономии, `deltaC` кандидата совпадает с независимым пересчётом, переносимым
набором С1/С2 являются только некритичные функции, у каждого домена не более
трёх вариантов разбиения, повторное применение кандидата С1 не порождает новый
совет для того же домена.

## 5. Метрики и «бюджет ДВБ»

`skib metrics` выдаёт, в том числе, бюджет доверенной зоны — ключевые числа для
оценки стоимости разработки и сертификационных артефактов:

```json
{"systemCost":486,"dvb":{"size":3,"cost":485,"costPercent":100,"boundaryEdges":2,"trustTransitions":1},
 "composition":{"domains":{"total":6,"internal":4,"external":2,"byTrust":{"ndb":1,"ddb":1,"ddbpcd":2}},
 "functions":{"total":7,"placed":5,"unplaced":2},"edges":{"total":6,"red":2,"green":4}},
 "goals":{"total":5,"red":1,"yellow":0,"green":4},"advice":{"count":8,"totalSaving":730,"totalSavingPercent":150,"bestSaving":140,"bestSavingPercent":29}}
```

Интерпретация: `size` — домены в ДВБ; `costPercent` — доля ДВБ в C_системы;
`boundaryEdges` — площадь границы доверия (объём спецификаций интерфейсов);
`trustTransitions` — переходы класса доверия (анализ каналов). Рост бюджета —
сознательное решение архитектора, а не побочный эффект правок. В блоке `advice`:
`totalSaving` — потенциал каталога независимых кандидатов (вариантный перебор
v0.03.01b даёт альтернативы, не сумму — показатель может превышать 100%),
`bestSaving` — лучший одиночный совет (гарантированно ≤ C_системы).

## 6. Контрольные примеры и правила для агента

- **Golden-примеры**: `samples/robot/state.yaml` — C_системы **486**;
  `samples/vessel/state.yaml` — **943**. Контрольные числа не должны меняться
  (проверяются тестами `advisor.test.ts`, `metrics.test.ts`, `make cli`).
- **Честная модель отчёта анализатора**: `tests/fixtures/vessel-user-state.yaml`
  — C_системы **335** (лидар — интерфейсный ДБ без forceTrusted, C_блока 3);
  советчик на ней воспроизводит «бонус» отчёта — посредник перед dom-4, −42.
- Правила: (1) после каждой структурной правки запускайте `skib validate`;
  (2) не выдумывайте id вне шаблона; (3) не задавайте `position`, если не требуется;
  (4) экономику изменений подтверждайте `skib metrics` до/после; (5) советы
  не применяются автоматически — кандидат можно воспроизвести через
  `adviceCandidate` (включая маршруты `downstream`/`gateway` разбиений) и записать в модель только с согласования человека.
- Интеграционные CLI-тесты: `npm run test:cli` (или `make test-cli`) —
  самостоятельный гейт без vitest (`tests/cli/run.mjs`), включён в `make check`.
- Системный промпт агента: достаточно разделов 1–3 этого файла + `skib schema`.

## 7. Что доступно только через GUI

Undo/redo, пан/зум канвы, геометрия рамок ЛГ, контекстные меню — интерфейсные
функции; движок их не требует. Автолейаут доменов (`computeAutoLayout`,
`src/engine/layout.ts`) доступен в GUI (кнопка «Раскладка»); CLI-команда —
в дорожной карте (docs/dev-roadmap.md, ряд P0).
