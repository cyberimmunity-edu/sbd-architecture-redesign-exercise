# Правила проекта «Моделирование СКИБ» (AGENTS.md)

Правила для разработчиков и ИИ-агентов, работающих с репозиторием.
Действуют по умолчанию; исключения фиксируются в CHANGELOG записи релиза.
Смежные документы: README.md, docs/developer-guide.md, docs/dev-roadmap.md,
docs/ai-integration.md (справочник ИИ-агента), docs/testing-guide.md.

## 1. Отчёты и документация — только Markdown (v0.03.01b)

- **Отказ от docx.** Новые отчёты, анализы, сводки и служебные документы
  создаются **только в формате Markdown** (`.md`). Генерация `.docx` (и
  отчётов в `.pdf`) не выполняется: md диффится в git, читается в CLI и
  без потерь попадает в поставку `make zip`.
- PDF-файлы в `docs/` (ТЗ, отчёт по трассировке) — исторические поставки
  ранних ревизий; источники истины — их `.md` версии. Новых PDF не создавать.
- Изображения для документов — PNG в `docs/img/` (или рядом с отчётом);
  диаграммы для отчётов — по правилам `scripts/` (matplotlib/PlantUML),
  текст отчёта — md со ссылками на них.
- Временные генераторы отчётов не сохраняются в `scripts/` без нужды:
  одноразовые скрипты удаляются после получения md.

## 2. Проверки — только через make

- Полный гейт перед сдачей: `make check` = проверка Makefile (сухой прогон)
  → lint (tsc + eslint) → смоук CLI (`make cli`) → интеграционные CLI-тесты
  (`make test-cli`, `tests/cli/run.mjs`) → unit (vitest) + E2E (Playwright).
- В чистой среде перед E2E: `npx playwright install chromium`.
- Рецепты Makefile — только с табуляцией; при текстовых правках запускать
  `python3 scripts/fix_makefile_tabs.py` и `make check-makefile`.
- Тест `tests/unit/makefile.test.ts` страхует состав `check` и .PHONY:
  новые цели добавлять и в .PHONY, и в сухой прогон `check-makefile`.

## 3. Контрольные числа и совместимость

- Контрольные числа примеров **не меняются**: robot — 486, vessel — 943
  (тесты `advisor.test.ts`, `metrics.test.ts`, `fixtures.test.ts`, `make cli`).
- Фикстура пользовательской модели `tests/fixtures/vessel-user-state.yaml`
  — честная модель «Безэкипажное судно-доставщик» (лидар без forceTrusted,
  C_блока 3): C_системы = 335 = база сводного отчёта анализатора.
- Формат файлов `version: 1` не расширяется ломающим образом: новые поля —
  опциональные, старые файлы читаются без ошибок (W-001 — неизвестные поля).
- Каждому коду E-/W- реестра `src/io/errors.ts` — ровно одна подсказка в
  `HINTS` (тест `hints.test.ts` не допускает пропусков и лишних записей).

## 4. Архитектура кода

- Движок отделён от интерфейса: логика — чистые функции в `src/engine` и
  `src/io`; UI (`src/ui`, `src/store`) — только отображение и действия.
  Транспорты (CLI `cli/skib.mjs`, будущие MCP/REST) — тонкие адаптеры над
  одними и теми же портами движка.
- Чистота и детерминизм: одинаковый проект — одинаковый вывод (советы,
  метрики, экспорт); перебор в порядке модели, сортировки по id/экономии.
- Интерфейсные строки — только в `src/i18n/ru.ts` (НФ-8); в коде и
  интерфейсе термин «сложность» не используется (`grep сложност src/` = 0).
- `forceTrusted` — полноправный признак модели (принудительный ввод
  внутреннего домена в ДВБ без критичной функции — необходимое условие
  работы функций безопасности других доменов, например доверенных
  датчиков), а не «трюк». Вынесенные части разбиений его не наследуют;
  у forceTrusted-домена с красным входом валидатор требует явного
  обоснования (W-013).
- Советчик (`src/engine/advisor.ts`): каждый совет — кандидат «что-если»,
  пересчитанный чистой `recalcCosts` (точная deltaC); автоприменения нет —
  решение за человеком. Кандидаты воспроизводимы `adviceCandidate`.

## 5. Релиз

1. Версия в трёх местах: `package.json`, `APP_VERSION` (`src/engine/types.ts`),
   `TAG` (`Makefile`) — рассинхрон ловят `makefile.test.ts` и `make cli`.
2. `CHANGELOG.md` — запись с секциями Добавлено/Изменено/Исправлено.
3. `docs/ai-integration.md`, `README.md`, `docs/dev-roadmap.md` — актуализировать
   при изменении CLI, схемы, советчика или правил.
4. Сборка поставки: `make check` → `make zip` → обновить `download/README.md`,
   удалить устаревшие артефакты из `download/`.
